# Milestone v0.6.0 — Enterprise Memory Backend

**Status:** planned · **Created:** 2026-08-04 · **Owner:** unassigned · **Depends on:** v0.5.0 (T4 telemetry, T10 playbooks, T13 promotion)

## Purpose

Give fleet memory a **backend port** with two implementations: the file-based one every user gets (JSONL runs, markdown playbooks, markdown ledgers — unchanged, still the default), and an optional **RelataDB** adapter for enterprise deployments that need semantic recall, provenance, bi-temporal history, cell-level ACL, and multi-tenant isolation.

Evidence: `docs/research/relatadb-memory-backend-2026-08.md`. Read it before starting any task — particularly §2 (licensing) and §3 (maturity), which together set the architectural constraint below.

**Theme: the architecture is the risk mitigation.** RelataDB is one month old, has one human author, zero public adoption, a private repository, and has been relicensed twice in twelve weeks. Its technical fit is genuinely strong and its BYOL licensing is clean — but none of that justifies structural dependence. So: a narrow port, file-based as the default *and only bundled* backend, and an adapter thin enough that abandonment or another relicense costs a deleted file rather than a rewrite.

## Commercial model: BYOL

The customer obtains and runs their own licensed RelataDB instance. fleetsmith ships **no** RelataDB code, no binary, and no vendored client — only an adapter that speaks REST to a customer-supplied URL. Under stock AGPL this is unencumbered (§0: "mere interaction … with no transfer of a copy, is not conveying"; §13 triggers on *modification*, not network use).

**Three rules, non-negotiable, enforced in CI:**
1. **Never ship or vendor the binary.** That is conveying, and the source obligation could not be met while their repo is private.
2. **Never patch or fork the engine.** That is the only §13 trigger.
3. **Always degrade to the file backend** — on connection failure, license expiry, or exhausted grace tokens. A fleet must never become unrunnable because a database is unreachable.

## Non-goals

- **No embedded/in-process mode.** RelataDB is a separate process; there is no Node-embeddable build.
- **No SDK dependency.** The memory surface is plain REST; native `fetch` covers it at zero added dependencies, preserving the single-runtime-dep property. The Apache-2.0 TS SDK stays a documented optional peer dep.
- **No migration of existing file state by default.** Import is opt-in and one-way (#T6).
- **No feature that only works on RelataDB.** Every capability the fleet depends on must have a file-backend answer, even a degraded one. Otherwise the OSS tier quietly rots.

## M1 — Memory port

**Context.** Today memory is implicit and scattered: `_fleet/runs/*/events.jsonl` (v0.5.0 T4), `_fleet/playbooks/*.md` (T10), `_fleet/notes/<agent>.md`, `LEDGER.md`. Nothing names the operations, so there is no seam to swap.

**Do.** Define `src/memory/port.js` — five verbs, deliberately mirroring RelataDB's vocabulary because it is sensible independent of backend:

| Verb | Meaning |
|---|---|
| `remember(item)` | persist an observation, lesson, or decision with provenance |
| `recall(query, {purpose, limit})` | retrieve relevant items |
| `consolidate()` | merge/dedupe; the ACE grow-and-refine step |
| `forget(selector)` | evict by rule (e.g. SkillMentor's utility < 0.05) |
| `justify(id)` | why does this item exist — the audit answer |

Every item carries `origin: human|evolved` (v0.5.0 T2) and an evidence list. `purpose` is required on `recall` — RelataDB rejects queries without a registered purpose (HTTP 400), and making it mandatory in the port keeps the two backends honest rather than letting the file backend accept queries the real one refuses.

**Accept when** the port is documented, has no backend-specific types in its signature, and a fake in-memory backend passes a shared contract-test suite.

## M2 — File backend

**Context.** This is the default and the only bundled implementation. It must remain fully functional forever — the OSS tier is not a demo.

**Do.** Implement the port over the existing artifacts: `remember` appends to the run log or playbook; `recall` does token-overlap ranking (no embedding dependency, same rule as `fleetsmith health`); `consolidate` runs the deterministic dedupe from T10; `forget` applies the eviction rule; `justify` returns the bullet's evidence list and counters.

**Accept when** it passes the M1 contract suite and every v0.5.0 feature that touches memory runs through the port with no behavior change.

## M3 — RelataDB adapter

**Context.** ~200 lines of `fetch` against `POST /memory/remember`, `GET /memory/recall`, `consolidate`, `forget`, `justify`. Gated on customer-supplied `RELATA_URL` + token. **Embeddings are caller-supplied on the ingest hot path** (since v1.1) — decide explicitly whether we generate them or send text-only and accept BM25-only recall. Recommend text-only for v0.6.0: adding an embedding dependency to a one-dep project needs its own justification.

**Do.** Implement the port; declare the SDK an optional peer dep, do not require it; **degrade to the file backend** on connection failure, 4xx from license exhaustion, or exit-78 conditions, with one clear warning and no run failure.

**Accept when** the M1 contract suite passes against a live instance; killing the instance mid-run degrades to file with a warning and the run completes; no RelataDB code is vendored (asserted by a CI check, per the licensing rules above).

## M4 — Playbooks as versioned procedure memory

**Context.** `ProcedureMemory` is a versioned instruction set with auto-incrementing `version` and `supersedes` chaining — precisely our ACE playbook, with the revision history flat markdown cannot give us. This is the single strongest technical argument for the integration.

**Do.** Map playbook bullets onto `remember_procedure` / `recall_procedure`, preserving the helpful/harmful counters and the advisory framing (v0.5.0 invariant 3: learned content is references, never rules). The file backend keeps its flat representation; the port hides the difference.

**Accept when** a playbook edit produces a new procedure version with `supersedes` set, and `recall_procedure` returns the current one — while the same code path on the file backend still produces a reviewable markdown diff.

## M5 — Promotion provenance

**Context.** v0.5.0 T13 writes `_fleet/evolution/decisions.jsonl`. The DGM safety argument turns on *traceable lineage* — it is what let the authors catch their agent deleting its own detection markers. `DecisionRecord` + `justify` + bi-temporal `AS OF` answer "why was this promoted" and "what did the system believe when it decided", which is genuinely painful over JSONL.

**Do.** Mirror every promotion decision into the memory port. Add `fleetsmith evolve --why <id>` returning the justification: the ops, the evidence, the eval deltas, and the verdict.

**Accept when** `--why` works on both backends (fuller answer on RelataDB, still useful on file), and a bi-temporal query answers "what was the playbook at generation N".

## M6 — Opt-in import

**Do.** `fleetsmith memory import` — one-way, explicit, idempotent, dry-run by default. Reads existing `_fleet/` state into the configured backend.

**Accept when** a repeat import creates no duplicates and a dry run writes nothing.

## M7 — Legal prerequisites

**Context.** Two open items from the evaluation. This gates the **public release** of the adapter, not its development.

**Do.** Obtain from ZySec AI, in writing:
1. **Trademark permission** to name the integration and use the mark in documentation. No trademark policy exists, and Apache-2.0 §6 affirmatively withholds trademark rights.
2. **A statement of intent on license stability** for a stated version range — the engine went Apache-2.0 → Elastic 2.0 → AGPL-3.0 in twelve weeks, with the last change shipped without its own ADR, and no CLA constrains the sole author from doing it again.

Also worth requesting: indicative pricing (the customer negotiates under BYOL, but we should be able to advise) and their position on node-bound license reactivation for containerized deployments, which is a real operational hazard at 24-hour manual issuance.

**Accept when** both are answered in writing, or the decision is explicitly taken to ship with purely nominative naming ("works with RelataDB"), which is unrestricted and not a blocker on its own.

## M8 — Docs and release

**Do.** Document the port, the two backends, the BYOL setup, and the degradation behavior. State the honest positioning: the file backend is complete and supported; RelataDB adds semantic recall, provenance, bi-temporal history, and multi-tenancy for deployments that need them. Record the three licensing rules where an implementer will see them.

**Accept when** a user can configure either backend from the docs alone, and the OSS path is demonstrably unaffected.

## Risks

| Risk | Evidence | Mitigation |
|---|---|---|
| **Vendor abandonment** | 1 human author, 1 month old, 0 stars, private repo | Adapter is ~200 lines behind a port; file backend is default and complete |
| **Another relicense** | Apache-2.0 → Elastic 2.0 → AGPL-3.0 in 12 weeks, last change without an ADR | BYOL means we never redistribute; M7 asks for written intent |
| **Accidental conveying** | AGPL §0/§6 | CI check that no RelataDB binary or source is vendored |
| **Operational friction** | Node-bound Ed25519 licenses, manual 24 h issuance, exit 78 | Degrade-to-file on expiry; document for containerized deployments |
| **Unvalidated quality claims** | Their own docs disclaim recall figures as synthetic-corpus | Do not repeat their benchmarks; measure recall against our own eval fleets |
| **OSS tier rots** | Common failure of open-core | Non-goal: no capability may be RelataDB-only |
